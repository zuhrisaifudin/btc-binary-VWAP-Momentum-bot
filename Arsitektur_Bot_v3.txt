sudah ada. Fokusnya: (1) jalur eksekusi WebSocket yang cepat dan fail-closed,

## FLOW UTAMA (event loop)

```
        ┌─────────────────────── Polymarket CLOB ───────────────────────┐
        │  WS market channel          WS user channel        REST order  │
        └────────┬────────────────────────┬──────────────────────┬──────┘
                 │ book delta              │ fill                 ▲ place/cancel
                 ▼                         ▼                      │
        ┌─────────────────┐      ┌──────────────────┐            │
        │ market_stream   │      │ user_stream (WS) │            │
        │ book in-memory  │      │ update inventori │            │
        └────────┬────────┘      └────────┬─────────┘            │
                 │ event "book berubah"    │ event "fill"        │
                 └───────────┬─────────────┘                     │
                             ▼                                   │
                  ┌─────────────────────┐                        │
                  │   QUOTE ENGINE      │                        │
                  │ 1. baca inventori   │                        │
                  │ 2. hitung quote     │                        │
                  │ 3. GUARDRAIL RUMUS  │────── lolos ──────────►│ executor
                  │ 4. place / skip     │────── ditolak ─► buang │
                  └─────────────────────┘                        │
                             ▲                                   │
                             └───────── fill balik ──────────────┘
```

**Langkah per event (dipicu book berubah / fill, BUKAN poll):**
1. **Baca inventori** market ini: `Su, Sd` (share Up/Down sekarang), basis biaya
   `cost_u, cost_d` → harga rata-rata `Pu = cost_u/Su`, `Pd = cost_d/Sd`.
2. **Hitung quote target** dari `quotes.py` (bid di sekitar mid book ± spread),
   untuk kedua sisi.
3. **GUARDRAIL RUMUS** (bagian inti — bagian berikutnya).
4. **Eksekusi**: yang lolos → `maker_executor` place/cancel (REST); yang ditolak
   → dibuang atau dikecilkan.
5. **Fill masuk** (WS user) → inventori diperbarui → kembali ke langkah 1.

## FLOW ORDER + RUMUS (inti)

Sebelum **tiap** bid dipasang, proyeksikan posisi seandainya bid itu keisi, lalu
uji dengan `pnl_formula`. Tujuannya: hindari market rugi-besar (mis. −$739 pada
data Bonereaper) yang muncul saat `Pu+Pd ≥ 1` atau imbalance tak terkendali.

```
              ┌─────────── kandidat bid: (sisi, harga p, size q) ───────────┐
              ▼
   Proyeksikan posisi PASCA-fill:
     jika sisi = UP :  Su' = Su + q ;  Pu' = (cost_u + q·p) / Su'   ; Sd'=Sd, Pd'=Pd
     jika sisi = DOWN: Sd' = Sd + q ;  Pd' = (cost_d + q·p) / Sd'   ; Su'=Su, Pu'=Pu
              ▼
   Hitung rumus (pnl_formula):
     modal'      = Su'·Pu' + Sd'·Pd'
     worst'      = min(Su', Sd') − modal'          # [4] risk-free?
     sum_price'  = Pu' + Pd'                        # [5] spread pasangan
     imbalance'  = |Su' − Sd'|
              ▼
   KEPUTUSAN (sesuai mode config):
     mode = risk_free_only  → PLACE hanya jika  worst' ≥ 0
     mode = spread_positive → PLACE hanya jika  sum_price' < 1   (pasangan untung)
     mode = off             → PLACE selalu (tiru Bonereaper apa adanya)
   plus cap universal:
     jika imbalance' > max_imbalance  → kecilkan size / geser harga / skip
              ▼
     lolos → executor place  |  gagal → skip bid ini
```

**Pseudocode keputusan:**
```python
def izinkan_bid(sisi, p, q, inv, cfg):
    # proyeksi posisi pasca-fill
    Su, Sd = inv.su, inv.sd
    Pu, Pd = inv.pu, inv.pd
    if sisi == "UP":
        Su = inv.su + q; Pu = (inv.cost_u + q*p) / Su
    else:
        Sd = inv.sd + q; Pd = (inv.cost_d + q*p) / Sd

    wc, risk_free = worst_case(Su, Pu, Sd, Pd)      # dari pnl_formula
    sum_price = Pu + Pd
    imbalance = abs(Su - Sd)

    if imbalance > cfg.max_imbalance:
        return False, "imbalance terlalu besar"
    if cfg.mode == "risk_free_only" and not risk_free:
        return False, "bukan risk-free"
    if cfg.mode == "spread_positive" and sum_price >= 1:
        return False, "Pu+Pd >= 1 (pasangan rugi)"
    return True, "ok"
```

**Kenapa rumus ini yang dipakai saat order:**
- `worst_case()` [rumus 4] = jaring pengaman: tolak order yang bikin market
  **bisa rugi** apa pun hasilnya. Ini yang membedakan bot disiplin dari Bonereaper
  (yang cuma 14,6% market-nya risk-free).
- `Pu+Pd < 1` [rumus 5] = syarat harga **untuk share yang sudah berpasangan**
  menangkap spread. Ia perlu, tetapi tidak cukup untuk menyatakan seluruh posisi
  aman: jumlah share Up dan Down masih dapat berbeda.
- `imbalance` [rumus 5] = kendali taruhan-arah telanjang; cap-nya mencegah ayunan
  seperti +$1.643 / −$739.

## Bagaimana Bot V3 Menghasilkan Uang dari Rumus

Bot tidak memperoleh laba karena sekadar menebak arah BTC. Pada market biner,
token pemenang bernilai $1 saat resolusi dan token lawan bernilai $0. Satu token
Up dan satu token Down dengan jumlah sama juga dapat di-*merge* menjadi $1
sebelum resolusi. Itu sebabnya sumber laba utama Bot V3 adalah membeli **dua sisi
pasangan** dengan biaya gabungan di bawah $1, bukan menumpuk satu sisi.
Mekanisme token dan *merge* ini mengikuti dokumentasi resmi
[Positions & Tokens Polymarket](https://docs.polymarket.com/concepts/positions-tokens).

```mermaid
flowchart LR
    A["Bid maker UP dan DOWN"] --> B["Fill masuk terpisah"]
    B --> C["PairedInventory: Su, Sd, Pu, Pd"]
    C --> D["M = min(Su, Sd): share berpasangan"]
    C --> E["D = |Su - Sd|: sisa arah"]
    D --> F["Laba pasangan = M x (1 - Pu - Pd)"]
    E --> G["Risiko hasil market: dibatasi max_imbalance / worst_case"]
    F --> H["Merge menjadi pUSD atau settle: satu outcome membayar $1"]
    G --> H
```

### 1. Rumus kas yang benar-benar dipakai

Untuk satu market, `PairedInventory` menyimpan share dan rata-rata biaya berjalan:

```text
Su, Sd     = total share Up dan Down yang sudah terisi
Pu, Pd     = rata-rata harga beli masing-masing sisi
C          = modal(Su, Pu, Sd, Pd) = Su x Pu + Sd x Pd
PnL_Up     = Su - C
PnL_Down   = Sd - C
worst_case = min(Su, Sd) - C
```

Ini persis fungsi `modal()`, `pnl_settle()`, dan `worst_case()` dalam
`src/mm/pnl_formula.py`. Rumus tersebut adalah **PnL bruto dari harga fill**;
ia belum memasukkan fee, rebate, slippage, kegagalan order, atau biaya operasional.

Pisahkan posisi menjadi dua bagian:

```text
M = min(Su, Sd)                         # share yang memiliki pasangan lengkap
D = |Su - Sd|                           # share satu sisi yang tersisa
laba_pasangan = M x (1 - Pu - Pd)       # decompose()["spread_pair"]
```

Jika `Pu + Pd < 1` dan `M > 0`, setiap satu share pasangan dibeli kurang dari
$1 lalu menghasilkan $1 saat di-*merge* atau ketika salah satu outcome settle.
Itulah spread maker yang ingin dikumpulkan bot. Jika `M = 0`, nilai
`Pu+Pd < 1` **belum menghasilkan laba pasangan** karena belum ada token lawan.

Bagian `D` adalah risiko arah. Contoh bila `Su > Sd` (net Up), PnL tepatnya:

```text
PnL jika UP menang   = laba_pasangan + D x (1 - Pu)
PnL jika DOWN menang = laba_pasangan - D x Pu
```

Jadi kondisi bebas-rugi bukan sekadar `Pu+Pd < 1`, melainkan
`worst_case >= 0`. Bentuk ekuivalennya untuk posisi net Up adalah
`laba_pasangan >= D x Pu`; untuk posisi net Down, gunakan `D x Pd`.

### 2. Contoh kecil: modal $20

Misalkan simulator menerima pasangan yang sama-sama berisi lima share:

```text
BUY UP   5 share @ $0.40  -> biaya $2.00
BUY DOWN 5 share @ $0.50  -> biaya $2.50

Su=5, Sd=5, Pu=0.40, Pd=0.50
C = 5x0.40 + 5x0.50 = $4.50
laba_pasangan = 5x(1-0.40-0.50) = +$0.50
PnL_Up = PnL_Down = $5.00 - $4.50 = +$0.50
```

Dengan modal simulasi $20, reserve $4, dan batas satu leg $2.50, operator dapat
menguji pola ini dengan:

```powershell
python scripts/simulate_paired_orders.py --mode risk_free_only --capital-usd 20 --reserve-usd 4 --max-order-usd 2.5 --min-shares 5
sim> pairusd 0.40 2.00 0.50 2.50
sim> show
```

Setelah satu pasangan, modal terpakai $4.50 dan budget simulasi tersisa $11.50.
Tiga pasangan seperti ini memakai $13.50 dan menyisakan $2.50 dari budget
$16. Contoh ini hanya simulasi matematika; harga, minimum size, tick, fee, dan
fill aktual harus selalu dibaca dari venue saat order hendak dibuat.

### 3. Contoh akumulasi nyata BTC 5-menit: Up dan Down tidak seimbang

Dua screenshot aktivitas market **Bitcoin Up or Down — August 4, 10:15PM–10:20PM
ET** memperlihatkan mengapa dashboard tidak boleh membaca PnL per token secara
terpisah. Angka UI telah dibulatkan; perhitungan berikut adalah estimasi dari
share, average, nilai posisi, dan transaksi redeem yang terlihat.

| Sisi | Share | Avg | Modal estimasi | Keadaan akhir pada screenshot |
|---|---:|---:|---:|---|
| Up | 262.00 | 13.9¢ | ~$36.44 | current $0; `-$36.44` |
| Down | 43.99 (UI membulatkan 44) | 72.5¢ | ~$31.88 | redeem 43.99 @ $1; PnL token `+$11.68` |

```text
Su = 262.00; Pu = 0.139
Sd = 43.99;  Pd = 0.725
C  ≈ $36.44 + $31.88 = $68.32

matched        = min(262.00, 43.99) = 43.99
imbalance      = 262.00 - 43.99 = 218.01 share net Up
Pu + Pd        = 0.864
spread_pair    = 43.99 x (1 - 0.864) ≈ +$5.98
worst_case     = 43.99 - 68.32 ≈ -$24.33
```

Down menang—terbukti oleh `Redeem` Down @ 100¢—maka hasil total **satu market**
adalah kira-kira `PnL_Down = 43.99 - 68.32 = -$24.33`, sebelum perbedaan
pembulatan dan fee. Keuntungan `+$11.68` pada kartu Down hanya laba token Down;
ia tidak menutup kerugian kartu Up `-$36.44`.

Contoh ini punya `Pu+Pd = 0.864 < 1`, sehingga 43.99 pasangan memang membawa
spread bruto positif. Namun ada 218.01 share Up tanpa pasangan. Saat Down menang,
kerugian exposure Up yang tersisa melebihi spread pasangan. Karena itu setiap
snapshot V3 wajib menampilkan minimal `matched`, `imbalance`, `spread_pair`,
`PnL_Up`, `PnL_Down`, dan `worst_case`—bukan hanya `Pu+Pd` atau PnL satu token.

### 4. Pengaman agar laba pasangan tidak berubah menjadi rugi

Untuk setiap kandidat BUY, `guardrail.check_buy()` atau `check_buys()` membuat
snapshot pasca-fill terlebih dahulu. Ia menerapkan urutan berikut:

1. Tolak jika `imbalance' > max_imbalance_shares`.
2. Pada `risk_free_only`, tolak bila `worst_case' < 0`.
3. Pada `spread_positive`, tolak bila `Pu' + Pd' >= 1 - pair_margin`.
4. Baru setelah lolos rumus, cek capital, reserve, minimum share, serta batas
   nominal per leg; kemudian executor boleh membuat order.

`risk_free_only` adalah mode paling ketat. Dari posisi kosong, satu BUY CLOB
tidak akan lolos mode ini karena belum memiliki pasangan. Pada CLOB, order Up
dan Down adalah dua order terpisah dan bisa terisi tidak bersamaan. Karena itu
`pair`/`pairusd` saat ini atomik **hanya dalam simulator**, bukan jaminan atomik
di bursa. Worker live harus memakai koordinator order pasangan dan pencatatan
reserve order terbuka, atau memakai `spread_positive` dengan cap imbalance yang
sangat kecil sampai mekanisme pasangan atomik tersedia.

`off` hanya untuk replay/analisis dan tidak boleh menjadi jalur order live.
`spread_positive` menjaga harga rata-rata pasangan, tetapi tetap dapat rugi pada
skenario buruk bila ada imbalance; ia bukan janji profit.

### 5. Dari laba teoritis ke kas yang benar-benar tersedia

Setelah fill, token dibukukan. Share yang sudah berpasangan dapat di-*merge*
menjadi pUSD tanpa menunggu arah, atau posisi dapat ditahan hingga resolusi lalu
token yang menang ditebus. Pembayaran $1 untuk token pemenang dan $0 untuk token
kalah adalah mekanisme resolusi resmi Polymarket.

Untuk order berikutnya, worker harus menghitung dua batas sekaligus:

```text
budget_sim  = capital_awal - reserve - C
budget_live = min(budget_sim, saldo_venue - total_notional_order_terbuka)
```

Istilah `total_notional_order_terbuka` berarti jumlah `harga x sisa share`
untuk BUY yang masih resting. Polymarket memang membatasi size berdasarkan saldo
dikurangi dana yang di-*reserve* oleh order terbuka, sehingga worker tidak boleh
menganggap saldo yang sudah dipakai ladder masih tersedia.
[Order Lifecycle Polymarket](https://docs.polymarket.com/concepts/order-lifecycle).

Dengan demikian urutannya jelas: **maker fill murah di kedua sisi -> terbentuk
M pasangan -> spread pasangan menambah PnL bruto -> D yang tersisa dibatasi ->
merge/redeem mengembalikan pUSD**. Tidak ada bagian rumus yang menghilangkan
risiko execution, imbalance, atau resolusi; semuanya harus terlihat di snapshot,
log keputusan, dan batas capital.

## Harga Masuk DINAMIS (saldo × rumus × waktu)

Harga bid **tidak statis**. Data menunjukkan dia mengutip di seluruh rentang
0,02–0,98 (termasuk lonjakan DOWN ~0,98 = beli favorit hampir-pasti menjelang
settle). Harga masuk harus dihitung dinamis dari tiga batas:

### 1. Batas dari RUMUS (jaga pasangan untung `Pu+Pd<1`)
Harga bid satu sisi **dibatasi avg sisi lawan** — bergerak otomatis:
```
p_bid_UP_max   = 1 − Pd − margin      # supaya Pu' + Pd tetap < 1
p_bid_DOWN_max = 1 − Pu − margin
```
Contoh bahaya yang ini cegah: kalau sudah pegang Up avg 0,05, maka beli Down @
0,98 → `Pu+Pd = 1,03 > 1` → **pasangan rugi**. Cap dinamis menolaknya
(`p_bid_DOWN_max = 1 − 0,05 − margin ≈ 0,94`). Jadi lonjakan 0,98 hanya boleh
saat sisi lawan **sangat murah** (Pu < 0,02).

### 2. Batas dari SALDO (capital / bankroll)
```
size_bid = f(saldo_tersedia, max_exposure, harga)     # pakai capital.py + risk.py
```
- Saldo menipis → size mengecil & ladder lebih pendek (jangan over-leverage).
- Modal terkunci di posisi = `modal(Su,Pu,Sd,Pd)` [rumus 1]; sisa saldo =
  `saldo_awal − modal`. Bid baru dibatasi sisa saldo.

### 3. Batas dari IMBALANCE + WAKTU
```
jika |Su−Sd| ≈ max_imbalance di sisi X → hanya bid sisi X di harga jauh lebih murah
mendekati expiry (profil waktu) → ikuti book ke ekstrem, TAPI tetap ≤ cap rumus
```

### Harga final = minimum dari semua batas
```python
def harga_bid(sisi, book, inv, saldo, cfg):
    p_target = book.mid_bid(sisi)                     # dari quotes.py (ikut book)
    p_cap    = 1 - inv.p_lawan(sisi) - cfg.margin     # batas rumus Pu+Pd<1
    p        = min(p_target, p_cap)                   # jangan langgar rumus
    size     = size_dari_saldo(saldo, p, cfg)         # batas bankroll
    if size <= 0 or inv.imbalance(sisi) >= cfg.max_imbalance:
        return None                                   # skip
    return p, size
```
→ **harga & size bid selalu = fungsi (book, inventori, saldo, rumus)**, bukan
konstanta. Ini yang bikin bot aman saat saldo kecil dan tetap menangkap spread.

**Config tambahan:**
```
price.margin           = 0.02    # jarak aman di bawah 1−P_lawan
capital.max_exposure   = <USD>   # batas modal terkunci (dari capital.py)
capital.saldo_awal     = <USD>
```

## Profil Waktu: kapan TAKER, kapan MAKER (jadwal eksekusi)

Diukur dari 80.188 fill nyata — role berubah **menurut detik ke expiry**. Ini
bukan acak; ini jadwal yang harus ditiru bot v3.

| detik ke expiry | fill | maker% | taker% | fase |
|---|---|---|---|---|
| **295–300 (buka)** | 1.545 | 18% | **82%** | **TAKER agresif** — rebut posisi awal cepat |
| 240–295 | 14.928 | 54% | 46% | campur, mulai maker |
| 180–240 | 16.298 | 61% | 39% | maker-dominan |
| 120–180 | 15.313 | 61% | 39% | maker-dominan |
| 60–120 | 16.003 | 66% | 34% | maker naik |
| 30–60 | 8.872 | 77% | 23% | maker |
| 15–30 | 4.582 | 80% | 20% | maker |
| **0–15 (akhir)** | 1.557 | **97%** | 3% | **MAKER murni** — likuiditas keluar |
| <0 (stlh expiry) | 1.090 | 100% | 0% | pasif total |

**Pola:**
- **Saat buka (5 detik pertama): 82% TAKER** — dia menyeberang spread untuk
  langsung dapat inventori awal saat book masih tipis/terbentuk.
- **Tengah window: ~60% MAKER**, makin ke expiry makin maker.
- **Mendekati expiry (<60s): makin MAKER (77%→97%)** — berhenti menyeberang spread
  (mahal + berisiko dekat settle), cuma pasang bid pasif → jadi penyedia
  likuiditas keluar buat yang cash-out.

**Implikasi bot v3 — mode eksekusi per FASE (dipetakan ke `secs_to_expiry`):**
```
t > 295s          → izinkan TAKER (seed posisi dua-sisi cepat saat buka)
60s < t ≤ 295s    → MAKER-dominan (quote pasif dua sisi, taker hanya rebalance)
t ≤ 60s           → MAKER-only (haram menyeberang spread; bid pasif saja)
t ≤ 15s / t < 0   → MAKER-only, size mengecil (cuma tangkap cash-out)
```
Ini masuk ke `QuoteEngine`: pilih mode taker/maker **berdasarkan waktu**, bukan
konstan. Konsisten dengan temuan fee: taker cuma dipakai saat posisi penting
(buka), maker dipakai saat edge fee-avoidance paling berharga (dekat expiry).

### Agresivitas (kapan dia menyeberang spread)
Agresivitas = **taker%** = `1 − porsi_maker`. Kurvanya **turun monoton** terhadap
waktu (bucket 30s):

| detik ke expiry | 270–300 (buka) | 240–270 | 90–120 | 30–60 | 0–30 (akhir) |
|---|---|---|---|---|---|
| porsi maker | 0,44 | 0,58 | 0,64 | 0,77 | **0,86** |
| **agresif (taker)** | **0,56** | 0,42 | 0,36 | 0,23 | **0,14** |

- **Paling agresif saat buka** (~56% taker di 270–300s, memuncak 82% di 5 detik
  pertama) — seed posisi cepat.
- **Makin pasif menuju expiry** (agresif tinggal 14% di 30 detik akhir).

**Bot v3:** agresivitas = **kurva menurun** terhadap `secs_to_expiry`, bukan
saklar. Peluang bot memilih taker (menyeberang spread) = tinggi saat `t`
mendekati 300, → 0 saat `t` mendekati 0.
```
p_agresif(t) ≈ clamp( (t − maker_only_below_s) / (300 − maker_only_below_s), 0, taker_open_max )
# taker_open_max ≈ 0.56 ; di bawah maker_only_below_s (60s) → 0 (maker-only)
```

**Config tambahan:**
```
schedule.taker_until_s   = 295   # di atas ini boleh taker (seed)
schedule.maker_only_below_s = 60 # di bawah ini maker-only
schedule.taper_size_below_s = 15 # kecilkan size di detik akhir
schedule.taker_open_max     = 0.56  # peluang taker maksimum saat buka
```

```
  (t>295)      (295 ↓ 60s: quote dua sisi)        (t<60s pasif)   (t<15s)
  82% taker    agresif turun 56%→23%              agresif 14%     size↓
     ▲                                                              ▲
  rebut posisi awal cepat                              cuma tangkap cash-out
```

### B. Detik pasar BUKA — urutan kejadian
```
┌───────────────────────────────────────────────────────────────────────┐
│ t = 300s  PASAR BUKA — book masih TIPIS & spread LEBAR                  │
└───────────────────────────────────────────────────────────────────────┘
  ① market_stream (WS) → snapshot book pertama:
        UP :  bid 0.40 | ask 0.55        DOWN: bid 0.45 | ask 0.60
                         └─ spread 15¢ ─┘

  ② QuoteEngine: secs_to_expiry=300 > 295  →  FASE = BUKA  →  TAKER diizinkan

  ③ Kandidat beli  →  GUARDRAIL cek tiap order (rumus):
     ┌─────────────────────────────────────────────────────────────────┐
     │ beli UP @ 0.55 (ambil ask, TAKER)                                │
     │   proyeksi: Su'=q, Pu'=0.55 ; Sd=0,Pd=0                          │
     │   Pu'+Pd = 0.55  < 1   ✓   saldo ✓   imbalance ✓                 │
     │   → ✅ PLACE (taker)  — dapat inventori UP awal                   │
     ├─────────────────────────────────────────────────────────────────┤
     │ beli DOWN @ 0.60 (ambil ask, TAKER)                              │
     │   proyeksi: Pu'+Pd' = 0.55 + 0.60 = 1.15  ≥ 1   ✗ PASANGAN RUGI  │
     │   → ❌ TOLAK ambil-ask                                            │
     │   → ganti: pasang BID DOWN pasif @ 0.44 (MAKER)                  │
     │        cap rumus: p_down ≤ 1 − Pu − margin = 1−0.55−0.02 = 0.43  │
     │        → bid @ 0.43   ✓  (jaga Pu+Pd<1)                          │
     └─────────────────────────────────────────────────────────────────┘

  ④ Posisi awal dua-sisi terbentuk, SEMUA dalam batas rumus:
        UP 0.55 (taker)  +  DOWN bid 0.43 (maker nunggu)

  ⑤ Transisi → FASE GRID MAKER: pasang ladder bid dua sisi
```

### C. Ladder maker setelah seed (grid dua sisi)
```
        harga
        0.60 │  ░ ask (tak disentuh)
        0.55 │  ● UP terisi (taker, saat buka)
   Pu+Pd<1   │
   dijaga    │  ┌ bid UP @0.50  ┐
             │  ├ bid UP @0.47  ┼─ ladder MAKER, requote tiap book gerak
        MID ─┼──┴───────────────┘
             │  ┌ bid DOWN @0.43 ┐   ← cap = 1 − Pu − margin
             │  ├ bid DOWN @0.40 ┼─ ladder MAKER
        0.00 │  └────────────────┘
             └────────────────────────────────────────► waktu (t menurun)
        setiap fill → inventori update → guardrail hitung ulang cap harga
```

**Cara baca:** saat BUKA bot menyeberang spread sekali untuk **seed** (● UP 0.55),
lalu **berhenti agresif** dan menebar **ladder bid pasif** dua sisi — tiap level
dijaga `Pu+Pd<1` oleh cap dinamis, size dibatasi saldo. Makin dekat expiry, ladder
makin rendah/kecil (fase maker-only).

## Akumulasi & Rumus (posisi yang BERKEMBANG)

Bonereaper tak beli sekali — dia **akumulasi terus** (81 fill/market). Artinya
`Su, Pu, Sd, Pd` **berubah tiap fill**, jadi rumus **dihitung ulang inkremental**,
bukan sekali.

### Avg = rata-rata tertimbang berjalan
Tiap beli `q` share sisi UP di harga `p`:
```
Su_baru   = Su + q
cost_u    = cost_u + q·p
Pu_baru   = cost_u / Su_baru        # avg yang kamu lihat di UI (mis. 33.6¢)
```
Ini persis `Inventory.apply_fill`. **Avg 33,6¢ di screenshot = hasil akumulasi
banyak beli**, bukan satu harga.

### Guardrail meng-GATE tiap langkah akumulasi
Karena `Pu+Pd` dan `worst_case` **bergeser tiap beli**, guardrail proyeksikan
state PASCA-beli **sebelum** order (lihat `izinkan_bid`):
- **Beli lebih di harga LEBIH TINGGI** → `Pu` naik → `Pu+Pd` bisa lewat 1 →
  **TOLAK** (akumulasi merusak).
- **Beli di harga LEBIH MURAH** → `Pu` turun → posisi membaik → **IZINKAN**.
- **Akumulasi satu sisi terus** → `imbalance` membengkak → dibatasi `max_imbalance`.

→ Akumulasi **tidak gratis**: tiap langkah diuji ulang. Rumus = **governor**
akumulasi.

### Contoh dari screenshot (BTC 11:10–11:15, Down menang)
```
Su=840.29 @ Pu=0.336   Sd=994.91 @ Pd=0.619
Pu+Pd = 0.955 < 1        → pasangan UNTUNG (akumulasi harga disiplin) ✓
matched=840, imbalance=155 Down
modal = 898.19
worst = min(840,995) − 898.19 = −57.90  → BUKAN risk-free (imbalance)
Down menang → payout 994.91 − 898.19 = +96.72
   (kalau UP menang → −57.90 ; dia pertaruhkan −58 utk +97)
```
Pelajaran: akumulasi harga **rapi** (`Pu+Pd<1`) tapi **imbalance** bikin tetap
berisiko. Bot kita bisa lebih ketat: batasi imbalance supaya akumulasi tak pernah
keluar dari `worst_case ≥ 0`.

### Aturan akumulasi Bot v3
```
tiap kandidat beli:
   proyeksi Pu'/Pd'/Su'/Sd' PASCA-fill      (running avg)
   izinkan HANYA jika  Pu'+Pd' < 1  DAN  imbalance' ≤ max_imbalance
                       (mode risk_free_only: DAN worst' ≥ 0)
   kalau harga beli menaikkan avg melewati cap → skip / turunkan harga bid
```
Bonereaper akumulasi **longgar** (cuma 14,6% market risk-free, 46,9% `Pu+Pd<1`);
bot kita **gate tiap akumulasi** → lebih disiplin dari dia.

## Tipe Order — Bonereaper (inferensi) vs Bot v3 (rekomendasi)

### Bonereaper pakai tipe apa?
**PENTING: on-chain (`OrderFilled`) TIDAK merekam tipe order** (GTC/FAK/post-only
itu level CLOB). Jadi hanya bisa **disimpulkan dari perilaku**, bukan dibaca pasti:
- **Fill maker (64%, nongkrong di book):** limit **GTC** yang rest — kemungkinan
  **post-only** untuk jamin maker + rebate. Dominan menjelang expiry (97%).
- **Fill taker (36%, seketika):** order marketable, terpecah jadi banyak fill kecil
  (150/32/18/1… share) = ciri **FAK** (isi yang tersedia di beberapa level, sisanya
  batal), bukan FOK.
- Tak bisa dipastikan tanpa riwayat order CLOB akunnya (tak tersedia untuk wallet lain).

### Rekomendasi Bot v3
| Fase | Peran | Tipe order | Kenapa |
|---|---|---|---|
| **Grid (mayoritas)** | MAKER | **GTC + Post-Only** | post-only **ditolak** kalau akan menyeberang spread → **jamin maker** (fee 0 + rebate), tak pernah tak sengaja jadi taker. Repo sudah punya fitur Post-Only. |
| Grid (opsional) | MAKER | **GTD = waktu settle** | auto-expire di t=0 → order basi bersih sendiri (pas market 5-menit) |
| **Seed saat buka** | TAKER | **FAK** | isi likuiditas yang ada, sisanya batal (partial OK) — pas "rebut posisi awal cepat". Bukan FOK (jangan all-or-nothing). |

### Dua catatan mekanis WAJIB dipertimbangkan
1. **Taker delay 250 ms di btc-5m up/down** (dari dok Polymarket): order taker
   **ditahan 250 ms**, **tak bisa dibatalkan** selama itu, lalu divalidasi ulang &
   match/reject. → jalur TAKER punya **+250 ms wajib** + risiko harga bergerak
   selama ditahan. Ini memperkuat: **pakai taker seminimal mungkin (cuma seed
   buka)**, sisanya maker. Cek per market: `GET https://clob.polymarket.com/clob-markets/{condition_id}`.
2. **Post-only = jaring pengaman ke-2**: walau guardrail rumus sudah cek `Pu+Pd<1`,
   post-only mencegah crossing tak sengaja di **level protokol** (kalau logika kita
   khilaf, protokol menolak).

### Sizing terikat saldo (dari dok — cocok dgn "harga masuk dinamis")
```
maxOrderSize = balance − Σ(openOrderSize − filledAmount)
```
Persis batas-saldo yang kita rancang: size bid ≤ saldo dikurangi order terbuka.
`MakerExecutor` WAJIB hitung ini sebelum place (jangan over-commit).

## Anggaran latency (jujur)

```
book berubah → terima WS   : ~20–80 ms   (RTT ke Polymarket)
inventori + rumus guardrail : <1 ms       (in-memory)
place/cancel → ACK CLOB     : ~30–100 ms  (RTT, REST)
────────────────────────────────────────
reaksi end-to-end           : ~50–150 ms  (10–20× > REST-poll)
```
Bukan sub-ms: CLOB Polymarket hosted, order-entry hanya REST. Yang cepat = sisi
**keputusan**.

## FastAPI: control plane, bukan jalur order

### Keputusan arsitektur

FastAPI dipakai untuk menjalankan lifecycle aplikasi, observabilitas, dan perintah
operator. Ia **tidak** menghitung quote pada request HTTP dan tidak memanggil CLOB
secara langsung dari router. Jalur trading tetap berupa worker per market:

~~~
CLOB market WS → book mailbox → MarketWorker → MakerRunner/guardrail → REST CLOB
CLOB user WS   → fill FIFO    ────────────────────────┘
~~~

Pilihan ini menjaga latency dan, yang lebih penting, mencegah refresh dashboard,
klien WebSocket yang lambat, atau request kontrol yang ramai mengubah urutan fill
dan keputusan order.

FastAPI dan worker hidup pada satu proses ASGI **dengan satu Uvicorn worker** per
akun bot. Jangan memakai --workers lebih dari satu: setiap process mempunyai
registry, WebSocket, inventori, dan order aktifnya sendiri. Untuk skala banyak
akun, jalankan satu process/container per akun; jangan menduplikasi akun dalam
beberapa process.

### Diagram aliran dan batas tanggung jawab

```mermaid
flowchart LR
    Operator["Operator / dashboard"] -->|"HTTP command"| API["FastAPI API"]
    API --> Registry["RuntimeRegistry\ncommand + snapshot boundary"]
    Registry --> Worker["MarketWorker\nsatu penulis state per market"]

    MarketWS["CLOB market WebSocket"] --> Book["MarketStream + OrderBook"]
    UserWS["CLOB user WebSocket"] --> Fill["UserFillStream"]
    Book -->|"latest book"| Worker
    Fill -->|"FIFO fill"| Worker

    Worker --> Core["MakerRunner\nquotes + risk + guardrail"]
    Core --> Exec["MakerOrderExecutor"]
    Exec --> Gateway["CLOB Gateway (REST, post-only)"]
    Gateway --> CLOB["Polymarket CLOB"]

    Worker --> Snapshot["MarketSnapshot immutable"]
    Snapshot --> Registry
    Registry -->|"GET /v1/*, /metrics"| API
    Registry -->|"WS snapshot terbaru"| Operator
```

Arah dependensi yang wajib dipertahankan:

~~~
api  ──baca snapshot / kirim command──► runtime ──► mm
infra ──menghasilkan event / melakukan I/O──► runtime
mm   ──tidak mengimpor FastAPI, infra, SDK CLOB, atau filesystem──► (murni)
~~~

Modul runtime boleh memakai port/antarmuka yang diimplementasikan infra. Sebaliknya,
FastAPI hanya mengenal RuntimeRegistry dan schema respons. Ia tidak boleh memegang
referensi MakerRunner atau adapter bursa.

## Kontrak state dan urutan event

### Satu penulis per market

MarketWorker adalah pemilik tunggal state mutable: book aktif, inventori pasangan,
order aktif, tracker toxicity, dan status pause/kill. Stream tidak pernah memanggil
runner.on_fill() langsung. Ia hanya menerbitkan event ke worker. Router FastAPI
juga tidak pernah menulis state; router menerbitkan WorkerCommand.

Dua jalur antrean dibedakan karena sifat datanya berbeda:

| Jenis | Penyangga | Kebijakan ketika penuh | Alasan |
|---|---|---|---|
| Book delta/snapshot | latest-value mailbox + Event | delta lama boleh diganti oleh book terbaru; jika sequence rusak, resync | quote hanya butuh keadaan buku terakhir yang konsisten |
| Fill | FIFO bounded queue | **fail-closed**: pause + cancel all + alarm; fill tidak boleh dibuang | satu fill hilang membuat inventori dan guardrail salah |
| Command operator | FIFO kecil + command id | tolak saat worker berhenti/queue penuh; tidak retry buta | command harus dapat diaudit dan idempoten |
| Snapshot dashboard | latest-value subscriber | snapshot lama boleh dibuang untuk klien lambat | UI tidak boleh memberi backpressure ke trading |

Urutan proses worker untuk setiap event:

1. Validasi umur dan sequence book; desync atau book tidak valid berarti cancel lalu
   menunggu resync.
2. Drain seluruh FillEvent lebih dahulu dan terapkan satu per satu ke
   PairedInventory. Dedup memakai trade/order id.
3. Terapkan command yang aman, misalnya pause, resume setelah preflight, atau reset
   session.
4. Ambil book konsisten terbaru, hitung fair value/toxicity/risk/quote.
5. Untuk setiap kandidat yang **menambah** Su atau Sd, guardrail memproyeksikan
   posisi pasca-fill dan memeriksa mode, imbalance, worst_case, dan Pu+Pd.
6. MakerOrderExecutor melakukan post-only/cancel-replace. Ia adalah pengaman
   terakhir setelah guardrail, bukan tempat strategi.
7. Publikasikan MarketSnapshot immutable, journal keputusan, dan update metric.

### Guardrail dan inventori pasangan

V2 memiliki InventoryManager dengan satu posisi net. Itu tetap dipakai untuk
kompatibilitas test/replay, namun tidak cukup untuk menghitung Su, Sd, Pu, dan Pd.
V3 menambahkan PairedInventory agar setiap fill fisik dicatat pada outcome yang
sebenarnya. Tidak boleh ada dua inventori mutable yang sama-sama menjadi sumber
keputusan.

Kontrak minimalnya:

~~~
OutcomeFill(outcome=UP|DOWN, side=BUY, size, price, trade_id)
PairedInventory.apply(fill) → PairedPosition
PairedPosition.snapshot() → Su, Sd, cost_u, cost_d, Pu, Pd
guardrail.check(candidate, position, config) → GuardrailDecision(allow, reason, projection)
~~~

Untuk masa transisi, worker menerapkan event yang sama ke akuntansi V2 hanya
sebagai pembanding/audit. Setelah hasilnya konsisten, PairedInventory menjadi satu
sumber posisi V3; pembanding lama dapat dihapus pada rilis terpisah. Pemetaan
token Down melalui complement.py harus terjadi **sebelum** OutcomeFill dibukukan,
supaya tanda posisi tidak terbalik.

dua kali.

| Method | Path | Tanggung jawab | Catatan keselamatan |
|---|---|---|---|
| GET | /health/live | process hidup | tidak menyatakan aman untuk trading |
| GET | /health/ready | preflight, worker, feed, dan snapshot siap | 503 bila live fail-closed |
| GET | /v1/markets | ringkasan semua worker | hanya snapshot |
| GET | /v1/markets/{slug} | book, quote, status, alasan terakhir | token/id sensitif disensor |
| GET | /v1/positions | Su/Sd/Pu/Pd, modal, PnL kedua settle, worst_case, matched, imbalance, spread_pair | nilai dari PairedInventory; tampilkan bruto dan reserve order terbuka secara terpisah |
| GET | /v1/guardrail/rejects | reject terbaru dengan reason code | buffer terbatas, bukan database |
| GET | /v1/config | konfigurasi efektif tanpa secret | hanya baca |
| POST | /v1/config/reload | validasi dan antrikan reload parameter yang diizinkan | tidak mengubah credential, mode live, atau market aktif |
| POST | /v1/markets/{slug}/pause | pause, cancel semua order, audit command | 202 + command id |
| POST | /v1/markets/{slug}/resume | minta worker menjalankan preflight lalu aktif | gagal tetap pause |
| POST | /v1/markets/{slug}/reset-session | reset kill/funding halt setelah operator memperbaiki sebabnya | harus diautentikasi |
| POST | /v1/markets/{slug}/cancel-orders | cancel eksplisit tanpa resume | 202 + command id |
| WS | /v1/ws/dashboard | push snapshot versi terbaru | slow client kehilangan frame lama, bukan event trading |
| GET | /metrics | Prometheus metrics | bind privat atau autentikasi proxy |

Tidak ada endpoint place-order, flatten, transfer dana, atau switch paper→live.
Flatten berpotensi menjadi taker dan membatalkan premis maker-only; bila dibutuhkan,
ia harus dirancang sebagai prosedur risiko terpisah dengan otorisasi eksplisit,
bukan diselundupkan ke router kontrol.

Endpoint kontrol wajib memakai token operator dari environment, misalnya
BOT_API_TOKEN, berkas log tidak boleh menyimpan token/secret, dan server secara
default bind ke 127.0.0.1 atau jaringan privat. CORS publik dimatikan.

## Lifecycle, performa, dan observabilitas

### Startup dan shutdown

1. app lifespan memuat konfigurasi, memvalidasi, dan menjalankan preflight.
2. Supervisor membangun gateway, stream, dan MarketWorker untuk setiap market yang
   diizinkan. Live gagal preflight berarti readiness gagal dan worker tidak quote.
3. Worker mulai dalam status PAUSED sampai book konsisten dan channel fill sehat.
4. Saat shutdown: supervisor mengirim pause, worker menghentikan placement baru,
   cancel semua order aktif, menunggu task dengan batas waktu, lalu menulis snapshot
   akhir/journal. Jika cancel gagal, process keluar dengan status gagal dan alarm.

### Anggaran performa

- Keputusan quote, guardrail, dan pembuatan snapshot tetap in-memory.
- Requote dibangunkan oleh event; debounce hanya di MarketWorker untuk membatasi
  cancel-replace, bukan polling tetap 300 ms.
- SDK CLOB yang sinkron dipanggil melalui executor/thread terkontrol dan **ditunggu
  serial oleh worker**. Jangan memanggilnya dari router atau membiarkan dua call
  memodifikasi order aktif secara paralel.
- HTTP client/WS session dipakai ulang; reconnect memakai exponential backoff dengan
  jitter dan batas maksimum.
- Market WS desync, fill channel stale, queue fill penuh, atau error gateway yang
  tak dapat diklasifikasi selalu fail-closed: cancel + pause + metric + log.
- Hindari database pada hot path. JSONL journal cukup untuk V3; database hanya
  ditambah bila kebutuhan query/audit lintas sesi telah didefinisikan.

Metric minimum: feed_age_ms, book_resync_total, fill_queue_depth,
worker_event_latency_ms, quote_decision_latency_ms, order_request_latency_ms,
guardrail_reject_total{reason}, orders_placed_total, orders_cancelled_total,
fills_total, worker_paused, dan kill_switch_active. PnL/position berasal dari
snapshot dan tidak menjadi satu-satunya indikator kesehatan.

### Dependensi dan kontrak eksternal

`fastapi` dan `uvicorn[standard]` sudah ada di `requirements.txt`. Tambahkan
`prometheus-client` saat `observability/metrics.py` dibuat. Tidak ada Redis,
database, atau message broker pada V3 awal: satu process/akun dan snapshot
in-memory membuat kegagalan serta ownership state tetap mudah dipahami.

Sebelum tahap WebSocket diimplementasikan, verifikasi endpoint, skema autentikasi,
urutan sequence, format snapshot/delta, dan kanal user CLOB terhadap dokumentasi
Polymarket yang berlaku. Jangan mengasumsikan kontrak dari REST SDK saat ini; jika
kanal user tidak menyediakan event yang diperlukan, fallback REST tetap wajib dan
worker harus tetap fail-closed ketika health fill tidak dapat dibuktikan.

## Konfigurasi V3 yang perlu ditambahkan

Config tetap satu sumber di config.json dan environment tetap tempat secret. Tambahan
yang diperlukan:

~~~
market_maker:
  guardrail:
    mode: risk_free_only       # risk_free_only | spread_positive | off (paper saja)
    max_imbalance_shares: 14
    pair_margin: 0.02
  capital:
    session_capital_usd: 20    # batas modal sesi; bukan saldo venue otomatis
    reserve_usd: 4             # dana yang tidak boleh dipakai bot
    max_order_usd: 2.50        # batas nominal satu leg BUY
    min_shares: 5              # contoh parameter; validasi minimum venue tetap wajib
  runtime:
    book_debounce_ms: 25
    fill_queue_max: 1_000
    reconnect_max_delay_s: 10
    shutdown_timeout_s: 15
  api:
    enabled: true
    host: 127.0.0.1
    port: 8000

# environment, tidak pernah dimasukkan ke config.json atau endpoint:
BOT_API_TOKEN=...
~~~

Mode off tidak boleh tersedia untuk live sampai ada keputusan risiko terpisah.
Reload hanya boleh menerima parameter yang sudah divalidasi dan harus memicu
cancel/requote atomik bila perubahan memengaruhi quote. Credential, URL CLOB,
market aktif, dan mode paper/live memerlukan restart + preflight baru.
Nilai `session_capital_usd` bukan pengganti pembacaan saldo venue dan reserve
order terbuka; jika keduanya tidak konsisten, worker harus fail-closed.

## Ringkasan keputusan

- FastAPI adalah host/control plane; MarketWorker adalah pemilik keputusan dan state.
- Book boleh diganti dengan snapshot terbaru, tetapi fill tidak boleh hilang.
- Rumus PnL tinggal di mm/pnl_formula.py dan hanya guardrail yang menerjemahkannya
  menjadi izin/tolak order.
- Laba bruto berasal dari `matched x (1 - Pu - Pd)`; imbalance adalah risiko arah
  terpisah dan hanya posisi dengan `worst_case >= 0` yang bebas-rugi pada settle.
- CLOB REST tetap satu-satunya jalur place/cancel, selalu GTC/post-only.
- Migrasi dilakukan dengan ekstraksi bertahap dari scripts/run_market_maker.py,
  bukan rewrite greenfield atau mengubah modul V2 yang telah teruji sekaligus.
